Encontré la race. Es un clásico check-then-act: el barrido decide hibernar y ejecuta la hibernación en dos pasos separados, sin sostener el candado de la sesión entre ambos.

En sweepIdle el reaper lee sess.lastActivity bajo sess.mu.RLock(), suelta el candado, y recién después llama a sess.hibernate(). En esa ventana la goroutine de la sesión puede recibir un frame nuevo, actualizar lastActivity y ponerse a trabajar — pero el reaper ya decidió, y hiberna un chat vivo. La comprobación de time.Since(...) ya quedó vieja para cuando adquiere el candado de escritura.

La ventana, paso a paso

InstanteGoroutine del barridoGoroutine de la sesión
t0Lee lastActivity, ocioso > 30 s → marca para hibernar—
t1Suelta RLockLlega un frame → escribe lastActivity = now()
t2Toma Lock y llama hibernate()Empieza a procesar (ya hibernada)

El fix es volver a validar el criterio dentro del mismo candado de escritura con el que se hiberna, de modo que la decisión y la acción sean atómicas respecto a lastActivity.

go · daemon/reaper/reaper.go 
func (r *Reaper) sweepIdle(now time.Time) {
    for _, sess := range r.sessions.snapshot() {
        sess.mu.Lock()
        idle := now.Sub(sess.lastActivity)
        // Re-validamos bajo el mismo Lock con el que hibernamos:
        if idle > r.idleTimeout && !sess.working {
            sess.hibernateLocked()
        }
        sess.mu.Unlock()
    }
}
